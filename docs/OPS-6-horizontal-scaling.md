# OPS-6: Горизонтальное масштабирование

## Результат

Docker Compose запускает две одинаковые реплики Spring Boot за одним nginx:

```text
клиент
  |
  v
nginx :80
  | round-robin
  +--> warehouse-app-1:8080
  |
  +--> warehouse-app-2:8080
```

Привязка клиента к определенной реплике отсутствует. Обе реплики используют один неизменяемый
образ приложения и общее внешнее состояние.

## Порты

| Назначение | Привязка на хосте | Адрес в Docker |
|---|---|---|
| Публичный API через nginx | `${PUBLIC_HTTP_PORT:-${SERVER_PORT:-8080}}` | `nginx:80` |
| Управление первой репликой | `127.0.0.1:${APP1_MANAGEMENT_PORT:-18082}` | `warehouse-app-1:8081` |
| Управление второй репликой | `127.0.0.1:${APP2_MANAGEMENT_PORT:-18083}` | `warehouse-app-2:8081` |
| Redpanda Schema Registry | `18081` | `kafka:8081` |

Порты приложения `8080` не публикуются на хосте. Это не позволяет обойти nginx и исключает
конфликт портов между репликами. Порты управления доступны только через локальный интерфейс.

Каждая реплика получает постоянный `INSTANCE_ID`. Spring передает его через свойство
`app.instance-id`, заголовок ответа `X-Warehouse-Instance`, теги метрик и структурированные логи.

## Запуск

Создайте `.env` из примера и укажите реальные учетные данные:

```bash
cp .env.example .env
docker compose up -d --build
docker compose ps
```

Команды для проверки:

```bash
curl -fsS "http://localhost:${PUBLIC_HTTP_PORT:-${SERVER_PORT:-8080}}/nginx-health"
curl -fsS "http://localhost:${APP1_MANAGEMENT_PORT:-18082}/actuator/health/readiness"
curl -fsS "http://localhost:${APP2_MANAGEMENT_PORT:-18083}/actuator/health/readiness"
```

Проверка готовности приложения учитывает доступность Spring, PostgreSQL и Redis. Kafka не входит в
группу проверки готовности, потому что в проекте нет отдельного индикатора состояния Kafka.
Публичный маршрут `/nginx-health` проксирует проверку готовности и остается успешным, пока готова
хотя бы одна реплика.

## Балансировка и обнаружение сервисов

Группа серверов nginx использует стандартный алгоритм циклической балансировки (round-robin).
`ip_hash`, файлы cookie и другие механизмы привязки клиента к реплике не настроены.

Встроенный DNS Docker указан в nginx как сервер разрешения имен. Группа серверов размещена в общей
зоне памяти, а для обоих серверов включен параметр `resolve`. Поэтому nginx обновляет адреса
контейнеров после пересоздания реплики без ручного перезапуска.

Ошибки соединения с вышестоящими серверами обрабатываются через `max_fails`, `fail_timeout` и
`proxy_next_upstream`. Параметр `non_idempotent` не включен, поэтому nginx не повторяет изменяющий
запрос после того, как запрос уже был передан реплике приложения.

## Наблюдаемость

Каждый проксированный ответ содержит:

- `X-Warehouse-Instance` - постоянный идентификатор реплики приложения. Если приложение не передало
  его, используется адрес выбранного вышестоящего сервера.
- `X-Warehouse-Upstream` - фактический адрес вышестоящего сервера, выбранного nginx.

Журнал доступа nginx записывает URI без параметров запроса, статус ответа, идентификатор реплики,
вышестоящий сервер и длительность обработки. В лог не попадают `Authorization`, тела запросов,
пароли и значения JWT.

Prometheus отдельно собирает метрики управления каждой реплики и добавляет метку `replica`. Алерты
различают недоступность одной реплики и потерю всех реплик. Метрики JVM остаются раздельными, а
бизнес-счетчики агрегируются по репликам. Grafana использует ту же модель.

Blackbox Exporter проверяет публичный маршрут готовности nginx. Отдельный критический алерт
покрывает недоступность балансировщика или потерю связи между ним и работающими репликами.

Promtail собирает логи обеих реплик и nginx. Метки сервисов Compose остаются доступны, хотя
контейнеры приложения не используют фиксированные значения `container_name`.

## Общее и локальное состояние

Состояние, влияющее на корректность, вынесено из процесса приложения:

- PostgreSQL хранит доменные данные, записи распределенных блокировок ShedLock и сессионную
  рекомендательную блокировку PostgreSQL для ручной обработки Kafka DLT.
- Redis хранит кеши Spring, токены обновления, список отозванных токенов доступа, результаты
  повторных запросов ротации и распределенные блокировки. Замена токенов, обновление списка
  отозванных токенов и публикация результата повтора выполняются атомарными Lua-скриптами, поэтому
  истечение блокировки не создает потерянные или частично записанные токены. Каждая refresh-пара
  хранит связь со своим access-токеном, поэтому обычная ротация отзывает только access-токен этой
  пары и не затрагивает другие активные сессии пользователя. Выход отзывает валидную пару токенов
  обновления и доступа одной операцией; access и refresh из разных сессий не принимаются как одна
  пара. Для пар, созданных до появления этой связи, первая ротация сохраняет новую пару в актуальном
  формате, а старый access-токен доживает свой исходный TTL: однозначно выбрать его среди нескольких
  сессий невозможно. Если параллельная ротация завершилась, выход
  находит ее результат и атомарно отзывает победившую пару. Массовый отзыв всех пар выполняется
  только при обнаружении reuse или явном вызове `revokeAllUserTokens` и атомарно обновляет ключи
  токенов, результаты повторов и индексы. Устаревшие записи активных индексов удаляются при входе, а
  параметр `JWT_MAX_ACTIVE_TOKEN_PAIRS_PER_USER` ограничивает размер индексов активных токенов
  обновления и доступа.
- Kafka хранит сообщения, состав групп потребителей и зафиксированные смещения.
- Consul хранит конфигурацию, общую для обеих реплик.
- Обе реплики получают одинаковый секрет JWT через переменные окружения.

Lua-скрипты для работы с токенами обращаются к нескольким ключам Redis в одной атомарной операции.
Поэтому предоставленная конфигурация использует одиночный экземпляр Redis. Redis Cluster не
поддерживается, пока все связанные ключи не будут использовать общий хеш-тег.

Счетчики Micrometer и ссылки на них в реестре локальны для процесса. Это допустимо: Prometheus
собирает метрики обеих реплик и агрегирует их при выполнении запросов. Локальное состояние метрик не
влияет на бизнес-корректность.

Планировщики, изменяющие общие данные, используют ShedLock. Очистка просроченных резервов, очистка
партий и обработчик outbox имеют только одно активное выполнение на весь кластер. Репозиторий
outbox дополнительно использует `FOR UPDATE SKIP LOCKED` для защиты на уровне строк.

## Быстрая проверка JWT без серверных сессий

Сценарий быстрой проверки выполняет следующие действия:

1. Ожидает готовность nginx.
2. Выполняет вход через nginx.
3. Хранит JWT только в защищенном временном файле.
4. Проверяет отсутствие `Set-Cookie` при входе и в каждом авторизованном ответе.
5. Отправляет авторизованные запросы товаров через nginx.
6. Требует получить как минимум два разных идентификатора реплик и адреса вышестоящих серверов.
7. Подтверждает, что JWT успешно обрабатывает реплика, отличная от выполнившей вход.
8. При очистке пытается выполнить выход, чтобы повторные запуски не оставляли тестовые пары токенов.

При интерактивном запуске учетные данные не попадут в историю команд:

```bash
./scripts/ops6-smoke.sh
```

Для работы скрипта нужны Bash, curl, awk, find и Python 3.

В CI передайте `OPS6_USERNAME` и `OPS6_PASSWORD` через хранилище секретов, отключите трассировку
команд оболочки и запустите:

```bash
./scripts/ops6-smoke.sh
```

Дополнительные настройки:

```bash
OPS6_BASE_URL=http://localhost:8080
OPS6_ATTEMPTS=8
```

Если `OPS6_BASE_URL` не задан, скрипт читает `PUBLIC_HTTP_PORT` из `.env`. Окружения, в которых
задан только `SERVER_PORT`, поддерживаются как резервный вариант.

Скрипт никогда не выводит пароль, токен доступа, тело ответа или заголовок авторизации.

## Восстановление базы данных

Перед восстановлением PostgreSQL остановите nginx и обе реплики:

```bash
docker compose stop nginx warehouse-app-1 warehouse-app-2
```

После восстановления запустите все три сервиса:

```bash
docker compose up -d warehouse-app-1 warehouse-app-2 nginx
```

Полная процедура описана в [POSTGRES_RESTORE_RUNBOOK.md](POSTGRES_RESTORE_RUNBOOK.md).
